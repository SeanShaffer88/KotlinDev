# Baseline Profiles — Example File

`baseline-prof.txt` here is a **tiny teaching example**, not a
profile to ship. Real profiles are generated by tooling (see
`../macrobenchmark/README.md` for the full flow) and contain
thousands of lines covering your critical user journeys.

## Reading the example

Each line names one class or method and starts with flags saying
how ART should compile it:

| Prefix | Meaning |
|---|---|
| `H` | Hot — called very often at runtime; compile it early |
| `S` | Needed during startup |
| `P` | Needed after startup (post-startup work) |
| `L...;` | A class descriptor, e.g. `Lcom/example/app/data/NotesRepository;` — include/initialize this class |
| (no flag before `L`) | Just the class rule; flags combine, e.g. `HSPL` = hot + startup + post-startup class |

Method lines give the full JVM signature:
`ClassName;->methodName(ParameterTypes)ReturnType`, e.g.
`onCreate(Landroid/os/Bundle;)V` is `onCreate(Bundle): Unit`.

So the example says, in plain words: "MainActivity's constructor and
onCreate are hot and needed at startup; the top-level ExampleApp
composable is a post-startup class to include; NotesRepository is
hot/startup/post-startup and its `notes()` Flow method is too."

## Rules of thumb

- **Generate, don't hand-write.** Use the baseline-profile Gradle
  plugin + a `BaselineProfileRule` journey test
  (`./gradlew :app:generateReleaseBaselineProfile`).
- Profiles live in the app module at
  `src/release/generated/baselineProfiles/baseline-prof.txt` (and
  `startup-prof.txt` for the startup-only subset) and are committed
  to git.
- Regenerate after major Compose/navigation changes, then verify
  with the macrobenchmark template in `../macrobenchmark/` —
  a profile that no longer matches the code quietly stops helping.
- Format details (flags, descriptors, wildcards) are specified in
  the official Baseline Profiles documentation; check it before any
  hand edit, and keep hand edits measured and minimal.
